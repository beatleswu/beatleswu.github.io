## Source findings and atomic seam

At this HEAD the public Rating projection is `_strip_question` (app.py:32340),
not `_rt_public_question`. It projects through `_g076_exposure_content` before
transforming when privacy is ON. `_rt_server_verify` (32021) uses the canonical
server SGF judge and session/question-derived transform. It does not trust
browser correctness. `rt_start` (32758) creates the original session/current
question token; `rt_resume` (32844) validates owner and returns the current
question. Anonymous sid remains a capability. `rt_answer` (32897) verifies
moves, locks `rating_test_sessions FOR UPDATE`, validates current question/token,
updates original estimate/answers/responses/mistakes and finalization, then
commits. Placement adventure unlock occurs AFTER its commit. The response
includes next question via `_strip_question` and a `best_move` field.

Calling the Flask `rt_answer()` view from a new blueprint is NOT atomic: it
opens its own connection, commits, and has a post-commit side effect. Wrapping
it in another request context or an outer SQLite transaction would not fix
that. No such wrapper is shipped as production integration.

`RatingServices` in `g076_rating_steps.py` is the typed integration seam:

1. `transaction()` owns one connection and one final commit, rolling back all
   exceptions, including callback/commit failures.
2. `resolve(conn, sid, uid)` locks the ORIGINAL session FIRST on that connection
   and checks existing owner rights on every open, step, and cached replay.
   It supplies the ORIGINAL current pool question/token and `_rt_transform_idx`.
3. `start(conn, uid, trigger)` retains original server selection, profile prior,
   placement and anonymous creation on that connection. The secure browser
   accepts only manual/placement intent; it cannot supply Elo or exclusions.
4. `settle(conn, ctx, server_moves, response_ms)` must extract/reuse ORIGINAL
   `rt_answer` verification and effects on that SAME connection. It receives no
   step/client correctness input, cannot commit, open another connection, or
   perform external I/O, and must repeat original current-question/owner checks.
5. Preserve post-commit placement unlock using reviewed transactional outbox or
   equivalent durable dispatch. Do not silently drop it or run it before commit.
   Review optional shadow observation separately from the rollbackable effects.

The fixture AST-loads original `rt_start`, `rt_resume`, `rt_answer`, the real
`_rt_server_verify`, transform and estimate functions without importing app or
starting its runtime. The deliberate seam adaptation removes `conn.commit()`
and supplies the caller connection. SQLite strips `FOR UPDATE` and serializes
writes using `BEGIN IMMEDIATE`. Selection uses two SYNTHETIC questions; rank
labels, finalization/unlock are fixture substitutes; limits are shortened to
two rounds. Those substitutes are NOT evidence for real placement, claims,
production selection, original route registration or PG locking.

## Candidate protocol

| Endpoint | Contract |
| --- | --- |
| GET `/api/g076/rating/capability` | Server-owned `legacy`, `steps`, or HOLD; no-store and Vary Cookie |
| POST `/api/g076/rating/start` | Only `{trigger}`; original session selection via service |
| GET `/api/g076/rating/resume/<sid>` | Current owner-scoped question and committed progress, never a new timer |
| POST `/api/g076/rating/step` | session_id, attempt_id, nonce, action, optional single move |

`G076_RATING_STEPS_ENABLED` and `G076_ANSWER_PRIVACY_ENFORCED` both ON admit steps.
Both OFF admit legacy. Partial/unknown configuration is HOLD. No other new mode
toggles are required. `services=None` under ON is HOLD (503), so G MASTER may
register capability before a reviewed settlement adapter exists.

Proposed schema lives as `SCHEMA` in the candidate helper, with NO automatic
migration or startup DDL. It contains attempts bound to original session,
question token, owner, transform and question bytes/metadata, plus unique
nonce/request-hash/response receipts. All steps require original-session lock
ordering. Only the caller's successful transaction makes replies visible.
Identical replay returns its persisted receipt; changed payload under the same
nonce conflicts. Replay must still pass current original owner rights. A changed
question revision under the same original question token causes HOLD rather
than resetting progress. Attempt id does not replace the original ownership
or current-question checks.

The initial allowlisted payload contains board-only transformed SGF and an
attempt cursor, never the original question token, solution tree, accepted
moves, best move or future reply. Resume includes only played stones, including
already committed opponent replies. The server replays stored history through
the existing step kernel, issues fresh nonce/deadline per continuation, and
rejects ambiguous/unsupported trees before opening. Explicit failure terminals
remain failure. Accepted-answer alternatives currently HOLD for review rather
than being silently narrowed. `katago_best_move` is not exposed or treated as
an alternative by this helper, consistent with `_rt_server_verify`.

Wrong moves are appended to server history. Timeout/give-up settle the current
partial history; early timeout is rejected, late moves cannot turn timeout into
success. Deadlines are server-owned and are not extended by resume/background
tabs. Terminal settlement calls the original authority adapter once in the
transaction, checks agreement, stores its receipt atomically, and opens the next
original question. If next-question preflight fails, the entire transaction
rolls back and remains HOLD; it never substitutes an easier question.

The page uses the secure paths only after server capability says steps. It
renders real WGo from the board projection, applies committed stones and
opponent replies, and resumes canonical round/results after terminal receipt.
It does not call legacy `answer` or `placement_finish` in secure play. Lost
responses retry the same body/nonce and recover via resume. HOLD retains the
stored session capability. Existing result/claim/anonymous handlers remain.
Origin checks reject cross-origin JSON writes; browser identity/flags/verdicts/
question ownership/history are not accepted as step authority.
